# 常见问题与排障

先让用户发 `/status`（或在 Web 看 Task 状态），根据状态判断。

## 1. Task 没反应

| 现象 | 可能原因 | 用户能做的 |
|---|---|---|
| `/status` 显示 🟢 running，很久没回复 | 在做长任务 | 耐心等；想打断发 `/esc`；想插入指示发 `/steer <内容>` |
| 🔴 stop | 空闲超时（1 小时）或被停 | 直接发一条消息即可自动恢复 |
| 回复“运行中的任务已达上限，请稍后重试” | 全平台并发上限 | `/stop` 掉自己不用的 Task，稍后再试；仍不行告诉管理员 |
| ⚫ clear | 已被清空，不可恢复 | 在会话主入口发消息会使用/创建新的主 Task；子 Task 话题里的消息会回到主 Task |
| 回复“该会话的 Agent 只响应创建者。” | 你不是该 Task 属主且平台配置为拒绝非属主 | 用自己的私聊/会话，或让属主操作 |
| 群里发的命令没有生效 | 你不是属主：命令按 untrusted 文本处理 | 让属主发命令 |
| 发了命令像普通消息 | 命令没在开头、大小写不对，或 `/stop` 等带了其他文字 | 单独发整条命令 |
| 发语音后没动静 | 正在转写；超长/失败会降级为文字说明+原音频 | 等待或改发文字 |
| `/status` 里“最近错误”有内容 | 引擎或模型错误 | 记下 Task 编号和错误原文，发 `/stop` 后再发消息重试；仍然失败联系管理员 |
| 消息发了完全没有任何回复，`/status` 也不回 | 平台服务异常（网关/控制器） | 联系管理员，告知时间和会话 |

## 2. Task 被 stop 了

- 空闲 3600 秒自动 stop 是正常行为，数据保留，发消息即恢复，上下文仍在。
- 主 Task 的非例行退出会收到“已退出（stop），原因：…，发消息会自动恢复。”的通知。
- 平台重启后，重启前 running/idle 的 Task 会收到“请继续”的平台消息并自动恢复。
- stop 超过 30 天会被自动清理（clear）。需要长期留存的数据放 `/data`。

## 3. GitHub 授权失效 / git 403

现象：Task 里 `git clone/push` 报 403/401，或会话里提示“授权已失效，请在飞书发送 /connect github”。

用户自己做：
1. 在飞书发 `/connect github`，按回复在浏览器打开链接、输入验证码授权。
2. 授权后让 Agent 重试（凭证每次现取，立即生效）。
3. 仍 403：确认你的 GitHub 账号有该仓库权限；组织若启用了 OAuth App 访问限制，需组织管理员批准该应用。
4. 提示“尚未连接 GitHub”（404）：Task 使用**属主**的授权，要由属主本人授权。

常见失效原因：同一用户/应用最多保留 10 个授权 token，反复重连会挤掉最旧的；在 GitHub 的 Authorized OAuth Apps 里撤销过；平台数据被重置。不要在对话里贴 token。

## 4. 部署后服务不通 / 平台服务异常

这类属管理员职责。用户能做的：
- 用 `/status` 与飞书里发一条消息确认是个别 Task 还是全平台没反应。
- Web 管理端打不开：确认地址；是否在待审批；告诉管理员。
- 向管理员提供：现象、时间、会话/Task 编号、`/status` 输出。**不要自己或让 Agent 执行重启/部署**（`/restart-service` 与 `restart_service` 仅管理员）。

管理员侧的检查入口（仅供告知管理员参考，不要代为执行）：服务健康检查接口 `/health`、compose 各服务状态与日志、`supai-admin check`；飞书出口 IP 需在应用白名单中（否则报 99991401）。详细步骤在部署文档，不在本手册范围。
